## 接手时的顺序

1. 进入实际目标仓库，核对 Git 根、branch、HEAD、index、工作树、origin 和适用规则。当前集成目录不是上述两仓的 Git 根，不在这里执行它们的发布命令。
2. 先接网页运行说明：实际克隆后读取该仓库 package.json、lockfile 与 Node/Vite 要求，执行其 `npm ci`、`npm test`、`npm run dev`。这些是外部网页任务的操作步骤，不是本次已经执行的检查。
3. 网页本地可加载与线上数据可用分别验收。记录 API 状态、broker_connected、最新 seq、样本时间、实板/模拟和实时/过期标记；不输出敏感历史内容。
4. AI 状态接口的 enabled/连通不等于实际 AI 问答通过。实际调用的额度消耗由该任务明确授权，不能把单次回答当硬件证据。
5. 首个改动建议为网页 README 运行说明纠正。网页 CI、main 规则、板端适配各自独立任务，不一次混改。
6. 只有明确的网页改动任务才在其特性分支执行 `npm run build`，检查 `docs/` 与源码对应；本机 cloud 没有这一构建入口。
7. 将组员 MicroPython 的温湿度/光敏/4G 成果与 C/HAL 分别保留、逐模块迁移。不要为网页接手刷板，也不要把旧包联网日志当作本机新固件的联网证据。

## Git 协作约定摘要

以下为用户方案建议，实际操作仍按目标仓库规则和执行者当前授权确定：

- 独立 GitHub 身份；可 fork 提 PR，或由所有者分别邀请两仓 collaborator，不共享登录态/密钥。
- 一项问题一张 Issue，一个可回退的逻辑改动一个 commit；仅暂存明确目标文件，检查 cached diff。
- main 保存可复现基线，短期分支承担改动；不清理别人未跟踪文件，不在共享分支随意 rebase/强推。
- PR 写明 Issue、变化范围、实际测试、证据等级、风险和回退方法，由另一位成员审查。合并后另验 Pages/线上服务。
- main 保护、必需 CI 等只有实际设置并验证后才记为启用。本次只提供本地模板，没有修改两仓设置。
- Git Skill 在独立来源仓库中；原文的 Antigravity/Codex 路径和托管块版本说明需要在执行者机器上再核对，不复制个人路径充当通用配置，也不自动把该 Skill 安装到本机。
